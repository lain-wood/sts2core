# L3 设计：构筑顾问

四块：合成战斗构造器（`synth.rs`）· 单场评估（`synth/eval.rs`）·
整幕链式评估（`synth/act.rs`）· MCP 接线（`bin/advise.rs` + `tools/advise_core.py`
+ `advisor/server.py`）。**实战里怎么读它的报告**在 [driving.md](driving.md)，
这份讲它为什么是这个形状。

## L3：合成战斗构造器（`src/synth.rs`，阶段 1）

```rust
pub fn build(spec: &FightSpec) -> Built;   // Built { state, gaps }
```

`(牌组, 遗物, 血量, 遭遇, 种子) -> State`，出来的是**第 1 回合的起点**：
洗过牌、发过手牌、回合开始的钩子跑过了。L2 从这里直接接手。

**为什么需要它**：对拍那条路上每个局面都是从观测同步来的（`Replayer::sync`），
而 L3 问的是**还没打的仗** —— 没有观测可抄，必须凭牌组和遗物搭出来。

### 它自己不实现任何游戏规则

用的是 `State::new` + `add_card` + `add_enemy` + `step::grant_relic` +
`begin_combat`，外加两张数据表（`content::RELICS` / `asc::ASC_HP`）。
**一条 `if 牌名` / `if 遗物名` 都没有** —— 有的话就说明表里缺东西。

### 三样它**故意**不猜，每样都报出来

| 拿不到的 | 处置 | 为什么不猜 |
|---|---|---|
| 遗物的跨战斗计数器（摆动球的相位） | 用 0，**报 `Gap::RelicCounterMissing`** | 0 是个具体的相位，猜错就是整场早/晚一个回合抽牌 |
| 敌人初始血量 | 从 `asc::hp_range` 的区间里掷（**它的第一个生产消费者**） | 表里没有这只就退回 `EnemyDef::max_hp` 并报 `Gap::NoHpRange` |
| 内核不认识的牌/遗物 | 照放，逐条报 `Gap` | 「不认识」和「没效果」是两件事 |

**血量掷点走一条独立的随机流**（`synth::hp_stream`），不碰 `State::rng` 的三条。
理由和不变量 4 的分流是同一句：掷血量在开仗之前，让它扰动洗牌流就等于
"换一只敌人的血"会改掉整局的抽牌顺序，**CRN 配对比较当场失效** ——
而 L3 的候选之间正是靠 CRN 比的。

### `SYNTH_ONLY_GAPS`：`modelled` 那一列问的是**哪条路**

`RelicDef::modelled` 一直被读成"这件遗物建好了没有"。它其实是
**「对拍路径上够不够」**：那条路上手牌 / 血量 / 药水槽全是观测量，`sync` 每帧照抄，
内核再建一遍就是重复计数（风箱和小血瓶的 `note` 里写着这件事，都是踩过的）。

**合成路径没有观测可抄**，于是这批"靠观测兜底"的遗物在那边一件都不生效。
差集就是 `content::SYNTH_ONLY_GAPS`，每条写着**它在开局那一刻少做了什么**，
由 `build` 报成 `Gap::SynthUnmodelledRelic`。
**几条走 [content.md](content.md) 那张表**（`count_content.py` 会数它），别在这里写死。

> **两条路两个覆盖率，这本身就是结论。** 同一件遗物可以「对拍够了」而
> 「合成不够」—— 只有一个 `modelled` 列的时候，这件事没有地方可写。

### `CONDITIONAL_START`：局外信息由**调用方**给

三件遗物的条件在**战斗观测里根本没有**：古茶具的「上一个房间是不是休息处」·
骨茶的「还剩几场」（[源码] `ShowCounter => false`，游戏连面板都不显示）·
缩放仪的「这一场是不是 Boss」。它们因此**不能进 `RelicDef::private_status`**
（那一栏是无条件挂的），走 `content::CONDITIONAL_START` + `FightSpec` 的三个输入
（`after_rest` / `RelicSpec::counter` / `boss_room`）。

> **「欠一个局外信息」有时候等于「欠一个参数」。** 这三件在 `modelled: false`
> 里挂了很久，理由写着"不在 L1 里"—— 对，但**在 L3 手上**：整幕链自己知道
> 在模拟哪个房间。2026-09-09 补的就是那个参数，不是机制。

**对拍路径一条都不挂**：那边能量/手牌/血量本来就是观测量，挂了就是重复计数
（风箱和小血瓶的 `note` 里记着这个坑）。

### `ENEMY_START_PLAYER_STATUS`：敌人给**玩家**挂的开局 status

`EnemyDef::start_status` 只装挂在它自己身上的那些，而 [源码] 里存在给对面挂的
（`Rocket.AfterAddedToRoom` 给玩家 `SurroundedPower`）。那一类走这张**按名字索引**
的侧表（今天 1 条），消费点是 `begin_combat`。

按名字不按下标：表增删不会漂，而拼错会被 `enemy_start_player_status_names_resolve`
抓住。**没给 `EnemyDef` 加一栏**是因为 73 条里 72 条是空的 ——
把一个稀疏事实摊成一列噪声。

### 遭遇表（`src/synth/encounters.rs`）

`data/encounters.json`（[源码] 幕→遭遇→怪物）+ `data/enemy_ids.json`
（[实录] 英文类名 ↔ 内核敌人）读进来，**只做查表和连接**，一条解析规则都没有。
类名 -> `kernel_enemy` -> `replay::enemy_id`（**名字解析只有那一处实现**，
`dump_encounters.py` 读的也是它）。

**它敢于放弃**：构成含随机的遭遇（`exact: false`）`resolve` 整条拒绝并说明原因 ——
编一个自洽的多重集出来是本仓库明令不做的事。认那一场仗时另有一条宽口径
（`identify` 的第二个返回值）：只要观测到的敌人全落在 `all_possible` 里就报
"构成含随机"，**和"唯一命中"分开报**。

**分布不是代表值**（2026-09-14）：构成随机、但分布在 [源码] 里逐支枚举得完的那几场（今天是盛碗虫两场），
在 `data/encounters_overrides.json` 的 `distributions` 里列出**全部**构成和权重，进表后是 `exact: false` + `variants`。
`resolve` 照旧拒绝它们（单场问的是「这一场」，答案不唯一）；整幕链走 `resolve_sampled`，每个样本按权重抽一支
（`act::variant_pick`，只吃 `(种子基, 样本, 房间)`，不和血量掷点共用一个数）。覆盖率要**每一支都开得出**（`can_open`）；
认遭遇时观测落在某一支上算唯一命中，**不退回宽口径**。见 verified-rules §2.18。

### `from_obs`：观测 -> `FightSpec`，两个台子共用一份

`synth_audit` 和 `fight_eval` 都要拿实录的第 0 帧搭同一场仗。这一步生在
审计台里（它当时是唯一的消费者），2026-09-10 搬进 `src/synth/from_obs.rs` ——
两边各写一遍的话，两个台子读出来的**就不是同一场仗**，而"哪个台子抽错了"
没有任何东西会报。

两处「第 0 帧已经不是开局那一刻」的修正也在里面，**两个台子都要**：
`DECK_REWRITERS`（风箱/骨茶/碎石者开局就把牌升了，照喂进去会**再升一次**，
所以整件扣下并报出来）· `corrected_hp`（`FightSpec::hp` 的语义是「**进这场仗
之前**」，而观测里小血瓶那 2 点已经回过了）。

## L3：单场评估（`src/synth/eval.rs`，阶段 2）

```rust
pub fn evaluate(spec: &FightSpec, cfg: &EvalCfg) -> FightEval;   // N 次采样
pub fn paired_delta(a: &FightEval, b: &FightEval) -> Option<PairedDelta>;
```

阶段 1 让内核**搭得出**一场还没打的仗，这一层把它**打完 N 次**。
报的不是一个分数，是一份分布：死亡率 · 终点血量 · 战损 · 回合数 · **截断率**。

### 判什么：死亡率在前，血量在后，**两者不许混在一个数里**

旧 advisor 的毛病是 ΔHP **在死亡处被截断** —— 一场两边都会死的仗里每个候选的
ΔHP 都塌向 0，排名恰好在最要紧的时候失声。所以这里：

* 死亡是**一个单独的计数**，不是"掉了很多血"的极端值；
* 血量分布的分母**只有打完并活下来的样本**，它答的是"活下来的话大概剩多少"；
* `paired_delta` 同样拆开：**只有 A 死 / 只有 B 死**的对数单独数
  （那才是"更安全"的直接证据），血量差只在**两边都活下来**的对上算。
  第一版没拆，86% 死亡的那场 Boss 当场被算成"升级之后更差" ——
  死掉那一侧的 `final_hp` 是 0 或负数，平均进去就是**同一个老毛病换了个地方犯**。

### 截断是**硬判据**，不是一栏诊断

撞上回合上限的推演**战斗没有分出胜负**，而它照样带着一个血量。所以截断的样本
**既不进死亡数、也不进血量分布**，单独计数，而 `bin/fight_eval` 在截断 > 0 时
**退非零码** —— 这是 L3 台子把守的唯一一个硬门。

> **别用抬高 `--max-turns` 去关掉它。** `Outcome::enemy_hp_left` 就是用来分辨
> 「差一口气」（接近 0）和「僵住了」（几百血）的，而僵住通常意味着**策略**
> 选错了目标函数 —— 用单回合的 `survive_first` 当跨回合策略实测 52/8320 条
> 只挡不打。默认策略因此是 `Policy::default()`（求解器 + `damage_first`）。

### CRN：共享的是**起点**，不是序列

样本 `i` 的种子只由 `(spec.seed, i)` 决定，**牌组进不来**（`eval::sample_seed`）。
于是两个候选在样本 `i` 上看到的**敌人血量逐字相同** —— `synth::hp_stream`
只吃 `spec.seed`。

**但共享到此为止**：牌组一换，洗牌流和敌人流**消耗的次数**当场就不一样
（仗长一个回合，敌人就多掷一次），两条流从那一刻起各走各的。
所以配对之后**逐场仍然有噪声**，判据要看**一批仗上的方向**。
实测（`--upgrade-check`，基础打击/防御全升，三个种子基）：
**血量那一维 79 场里 69–73 场为正、均值 +2.3～+3.1**，方向稳；
**死亡那一维救回 93–99 / 反而死 36–60**，比值只有 1.6～2.4:1。
⇒ **死亡率是噪声最大的那一维，而它正是 L3 要判的东西**，
阶段 3 得按这条排采样预算。

### 每个样本各 `build` 一次

不是"搭一次然后换种子推演"：敌人血量是 `asc::hp_range` 掷出来的，
**40 血的小怪和 48 血的小怪不是同一场仗**，搭一次就把这条方差冻掉了。
代价是每个样本多一次 `build`（微秒级，79 场 × 64 样本共 1.1 秒）。

### 已知偏差**从这副牌组自己算**（`eval::Caveat`）

不是一段写死的免责文本 —— 那种东西会被读者跳过。四条各带着数：
牌组里几张能力牌（引擎牌评不到 ⇒ **低估**）· 身上几瓶药水（推演一瓶都不喝
⇒ **低估**）· 构造器报了几条缺口 · **A8 以上**（进阶数值整张表是 `[源码]` 档，
全部实录是 A1/A2）。没有能力牌的牌组不会看见第一行。

## L3：整幕链式评估（`src/synth/act.rs`，阶段 3）

```rust
pub fn evaluate_act(spec: &FightSpec, plan: &ActPlan, t: &Table, cfg: &ActCfg) -> ActEval;
pub fn paired_act_delta(a: &ActEval, b: &ActEval) -> Option<ActDelta>;
```

阶段 2 把**一场**仗打完 N 次，这一层把**一整幕**串起来走 N 次：
遭遇按 [源码] 的分布抽、**血量跨场累计**、死在第几间单独记。
路线图给 L3 定的判决（「走完这一幕的死亡概率」）到这里才问得出来。

### Boss 钉不钉：**局外已知的东西不该掷骰子**（2026-09-12，阶段 4）

`ActPlan::pin_boss` 给了就不掷。实战里这是个**已知量** —— 地图屏一进去就写着
这一幕的 Boss 是谁（mod 的 `map.boss.id`，[源码] `ActModel.BossEncounter`），
而 Boss 那一场是整幕死亡率里最大的一块：掷一个均匀的 Boss 等于把一条已知信息
换成方差。

**这是阶段 1 那句「欠一个局外信息有时候等于欠一个参数」的第四条**
（前三条是 `after_rest` / `RelicSpec::counter` / `boss_room`）。

两条守着它的性质，各有一个测试：

* **钉错幕的 Boss 整个拒绝作答**（`ActRefusal::NoSuchBoss`）。退回去掷一个的话，
  报出来的数会像是"按你说的那只算的"
* **钉了不许扰动这条链的其余部分**：抽 Boss 原来要掷一次骰子，跳过它却让后面的
  抽牌漂掉，就等于"钉 Boss"顺手换了整幕的遭遇 —— 而两个候选之间的 CRN
  正是靠那一维。（今天 Boss 是最后抽的，所以天然不漂；测试钉住这件事，
  免得以后往后面加抽什么。）

### 路线**不建**，由调用方给

`ActPlan::rooms` 是一串房间（`M` 杂兵 / `E` 精英 / `B` Boss / `R` 休息处），
「走哪条路、走几间、在哪歇」是局外决策，路线图第一刀就划在外面。
房间类型**只有这四种** —— 商店/事件/宝箱对战斗链是空操作，
写进来只会让人以为建了。
`bin/act_eval` 的默认路线是一个 **`[判断]`**（8 杂兵 + 1 精英 + 3 休息 + Boss），
**打印在报告最上面**，`--rooms` 随时换掉。
**不要从语料条数去数「这一幕打几场」** —— 录制是抽查的（家规：精英+Boss 必录），
trace 数系统性小于真实战斗数。

### 抽序列照 [源码] `ActModel.GenerateRooms` 的**分布**

前 `NumberOfWeakEncounters` 场从弱怪池抽、其余抽到 `BaseNumberOfRooms` 场、
精英预抽 15 场、Boss 均匀取一个（A10 的第二个 Boss 在其余里再取一个，
**只有最后一幕**）。`GrabBag` 权重全是 1 ⇒ 等价于「在满足谓词的那些里等概率抽、
抽完拿走」；`AddWithoutRepeatingTags` 不许和上一场共享 tag。
**随机流本来就不和游戏一致**（不变量 4），这里要的是分布对。

> **弱怪和普通怪进的是同一个输出列表**，所以普通池抽的第一场要和
> **最后一场弱怪**比 tag。分成两个列表的话，「连着两场史莱姆」
> 会在唯一需要这条约束的地方漏掉。

### 开不出来的那一场：**跳过并计数**，不是不存在

抽序列**故意不按"内核认不认识"过滤** —— 过滤掉就等于
"这一幕只有内核认识的那几场"，那是个静默的谎。抽到开不出的就
**这一间不打、计一笔 `ActSample::unsimulated`**，血量原样带下去。
方向因此是**乐观**的（少挨了几场打），所以 `ActEval::coverage` 和
`unsimulated` **必须和结论并排印**。今天平均每条链漏 0.2 场（2026-09-13 补完第 3 幕六只之前是 2.5；
09-14 摘掉两条错定义时一度涨到 2.2，数变大是因为那两场从「算错」变成了「跳过」；同一天深夜补齐 Hive 之后 1.5，
09-15 第 1 幕批 0 把六场构成随机的仗进表之后 0.8，09-17 第 1 幕两只 Boss + 墨宝进表之后 0.6，
09-19 暗港补齐之后 0.2，同一天密林两场杂兵进表之后 **0.1** —— 只剩第 3 幕女王）。

### 休息处：[源码] 0.3×上限，向下取整

`HealRestSiteOption.GetBaseHealAmount = MaxHp * 0.3m`，落地那一步
`SetCurrentHpInternal` 是 `(int)Math.Min(hp + amount, MaxHp)`。
73 血上限回 **21**（不是 22）。`Hook.ModifyRestSiteHealAmount`（有遗物改这个数）
**没建**，方向是低估自己。

### CRN：比单场**多共享一维**，而那一维买下了整个判决

阶段 2 量到「死亡率是噪声最大的那一维」，并把方差缩减留给了这一层。
多共享的正是路线图点名的那个：**「这一幕抽到哪几场遭遇」**
（`seq_seed` 只吃 `(base, i)`）＋**逐场敌人血量**（`fight_seed` 只吃 `(base, i, k)`）。

**它值多少，量过**（`--upgrade-check`，基础牌全升，78 副牌组 × 64 条链）：

| | 救回来的链 / 反而死掉的 | 比值 |
|---|---|---|
| CRN 开（默认） | 529 / 66 | **8.0 : 1** |
| `--crn-off`（B 臂换一条随机流） | 1138 / 712 | 1.6 : 1 |
| 单场版本（`fight_eval --upgrade-check`） | 93–99 / 36–60 | 1.6–2.4 : 1 |

> **关掉 CRN，整幕的死亡那一维当场掉回单场的水平。**
> 所以这个判决是**方差缩减**买来的，不是"一条链里有好几场仗、信号更多"
> 买来的 —— `ActCfg::crn_salt` 那个旋钮存在的唯一理由就是把这两件事分开。
> **阶段 2 那个问题（加样本还是方差缩减）的答案是后者。**

### 两个配对入口：换牌组的和换路线的

`paired_act_delta` 要求**同一条路线**（比牌组的时候路线必须固定，换了就不是
同一个问题了）。但「走不走精英」本身就是一个决策，而它**只能**由两条不同的
`rooms` 表达 —— 所以那一对走 `paired_act_delta_across_routes`
（前者查完路线就调它，逻辑只有一份）。

**两个入口共享的 CRN 不一样，报告里要说**：换路线那一对仍然共享
「这一幕抽到哪几场遭遇」（`seq_seed` 只吃 `(base, i)`），但**逐场敌人血量
那一维在路线错位的那一刻就分岔了**（`fight_seed` 吃房间下标 `k`）。
所以它比换牌组那一对噪声大，`bin/advise` 会在那一行标出来。

### 截断：整条链作废

一场仗撞上回合上限**没有分出胜负**，而它照样带着一个血量；带进下一场，
后面每一场都建在假前提上。所以链停在那里，整个样本既不进死亡数也不进
血量分布 —— 和 `eval` 对单场的处置是同一条，`bin/act_eval` 守那道硬门。

### 回溯检验：**它判的是偏的方向，不是内核对不对**

路线图给阶段 3 定的独占判据。每条实录是一个 `(真牌组, 真遭遇, 真战损)` 样本，
拿预测的战损分布去包它。`fight_eval` 当初拒绝做这件事的两个理由今天仍然成立，
所以是**带着它们读**：

* trace 末帧不保证是战斗结束 ⇒ **只认末帧落在战利品/选牌界面且场上没有敌人**的那些
  （78 条里 71 条够格，其余逐条报"为什么不算"）；
* 实测那一场是**玩家**打的、这里跑的是**我们这套策略** ⇒ 覆盖率是
  「玩家 + 策略」两个差的**合量**，读成"内核准不准"就错了。

**那它判得了什么：偏的方向和大小。** 今天的读数是
**预测每场比实测多掉 6.7 血**（2026-09-19 之前 7.2），分位数排名直方图重重地堆在左边
（27/70 落在最低那一档）—— 我们这套策略比玩家费血。
**整幕链的结论正比于这个偏差乘以场数**：一幕打 5 场就是 30 多点血，
整幕死亡率要带着这一条读。

> **7.2 -> 6.7 那一截是一个 L2 错，不是策略弱**（2026-09-19）：最大的离群点 `act1_f12_elite_phrog`
> （预测九成死、玩家 −1 血）是叶评估不数死时召唤、求解器不肯收宿主，修了就 0 死。
> **偏差里剩下的那部分还没拆过**：离群点先查一遍是不是同类的错，再把它读成「策略比玩家费血」。

## L3：MCP 接线（`src/bin/advise.rs` + `tools/advise_core.py`，阶段 4）

```text
游戏 ──HTTP──► tools/advise_core.py ──JSON/stdin──► target/release/advise ──► 一份人读的报告
               （脏活：读状态、认牌名、挑候选）      （L3：evaluate_act / evaluate + 配对比较）
                                                            ▲
                        advisor/server.py（八个 MCP 工具，只做映射）
```

和 `solve_now.py -> solve --live` **同一条路**（独立可执行文件 + JSON/stdio），
理由在 [`../CLAUDE.md`](../CLAUDE.md) 的「构建与环境」：这台机器是 GNU 工具链，PyO3 过不去，而边界调用本来就少。

### 一条命令答四个决策，靠的是「候选」这一个概念

拿牌 / 移除 / 升级 / 走不走精英，在 L3 眼里是同一件事：
**一副基准牌组 + 若干个改动，在同一批随机上配对比**。所以请求里只有一种东西：

```json
{"label": "拿「铁甲」", "add": [{"name": "铁甲"}], "remove": [3], "upgrade": [5], "rooms": "EMRB"}
```

**候选按下标寻址**（不是按牌名）：三张打击里带附魔的是哪一张，名字答不了，
而挑哪一张是调用方的事。**内核只认下标**，名字只进标签。

三个问法共用这一份请求：`act`（走完这一幕会不会死，L3 的判决量）·
`fight`（这一场从**开局**打完会怎样）· `deck`（**一次推演都不跑**，
只报内核看见了什么）。

### 它**故意**不做的三件事

| 不做 | 为什么 |
|---|---|
| 不认牌名以外的游戏文本 | 牌名 -> 内核的牌只有 `synth::card_from_name` 一处实现（和 `replay::sync` 共用），这里再写一份就是两份 |
| 不建路线 | 路线图第一刀就划在外面。`rooms` 由调用方给，**连同"它是怎么来的"回显在报告最上面** |
| 不挑候选 | "奖励屏上是哪三张"是局外信息，Python 侧读得到，内核读不到 |

### 主信号是 0 的时候**另开一栏**，不是沉默

死亡率是判决量，而**基准必死**的牌组上它恒等于 0 —— 那正是旧 advisor
「ΔHP 在死亡处被截断」那条老毛病换了个地方犯。出路不是把两个量混成一个分数
（那就是老毛病本身），是另开一栏，**只在主信号是 0 的时候印**：

* 整幕：两边都死的链上，候选**死得更靠后**（多走了几间）的对数
* 单场：两边都死的样本上，候选结束时**敌人剩的血更少**（差一口气 vs 打不动）

冒烟时它当场兑现了一次：起手牌组打第 1 幕 Boss 两臂都是 64/64 死，
而「基础打击全升」在 63/64 条配对样本上把敌人剩血压低了 **21 点** ——
主信号一个字都说不出来的地方，这一栏说得出方向。

### Python 那一侧只做翻译，但有两件**内核办不到**的事

1. **「这是哪一幕」**：内核的遭遇表按幕名索引，而 `run.act` 只有 1/2/3 ——
   **第 1 幕有两个**（Overgrowth 和 Underdocks 同序号）。唯一分得开的是
   **地图屏**报的 Boss id，而卡牌奖励屏上没有地图块。所以 `advise_core`
   看见地图就记一份到 `traces/_advise_ctx.json`，看不见就用那份缓存
   （换幕、或者**楼层倒退**——那是新开了一局——就作废）。
   **两个都没有就说认不出来**，不挑一个自洽的幕名。
2. **「还剩几间房」**：默认路线按地图上 `boss.row − 当前 row` 截尾
   （一行一间房）。**它是个 `[判断]`**，和 `bin/act_eval` 的默认路线同源，
   所以每份报告都把它和"它是怎么来的"一起印出来。

### 知识的诅咒：**8 种选法由这一层比，L2 不定价**（2026-09-14）

第 2 幕 Boss 知识恶魔的三次二选一是**玩家的决策**。内核把它做成策略参数
（`State::curse_policy`，第 k 位 = 第 k 次选瓦解），`FightSpec::curse_policy` 由调用方给，
没人给就是 `content::DEFAULT_CURSE_POLICY`（玩家判定：第二次一般选瓦解）。

* **单场问法**（`question: fight`，`boss_requirement` / `inspect_fight` 走的就是它）：只要这场仗里有
  `content::offers_curse_choice` 的敌人，报告末尾多一张表 —— 另外 7 种选法和默认选法**在同一批随机上配对比**
  （`paired_delta`，排序和候选表同一套）。**推演从开局到底按同一种选法打**，不看局面临时换。
* **整幕问法**：按默认选法打，钉住的 Boss 是它时报告里印一句「8 种对比问单场」。
  没有在整幕链里 ×8 —— 一条链里只有 Boss 那一间受它影响，而配对比较要的是换选法、其余不动。
* **为什么不是 `Pending`**：选牌屏开在敌人回合中间，`step(EndTurn)` 是原子的；
  价值全在后面几个回合，单回合求解器定不了价 —— 和跨回合药水拒绝评分同一个理由。

### 它**不进那九条验收**

`synth_audit` / `fight_eval` / `act_eval` 是**验收台**：测试集是实录，判据是红不红。
这个是**生产入口** —— 测试集是"现在这一局"，没有红绿，只有一份带着缺口清单的报告。
它的正确性由它调用的那三层的验收背书；它自己那一层（请求解析、候选落盘、排序）
由单测和一次离线冒烟（喂一份手搓的实况 JSON）盯着。
