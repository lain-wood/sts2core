# 验收

改完内核**每次都跑全套**，不只是 `cargo test`。这份讲每一条跑什么、判什么、
为什么非它不可；**最近一次的读数**在下面「当前基线」，历史读数在
[verification-log.md](verification-log.md)。

## 默认那套：`cargo test` + 九次对拍运行

```bash
cargo test --release
cargo run --release --bin verify  -- traces/act*.json traces/synthetic_*.json
cargo run --release --bin verify  -- traces/act*.json traces/synthetic_*.json --per-turn
cargo run --release --bin verify  -- traces/act*.json traces/synthetic_*.json --predict-enemy
cargo run --release --bin solve   -- traces/act*.json
cargo run --release --bin rollout -- traces/act*.json
cargo run --release --bin rollout -- traces/act*.json --policy fast
cargo run --release --bin synth_audit -- traces/act*.json traces/synthetic_*.json
cargo run --release --bin fight_eval  -- traces/act*.json traces/synthetic_*.json
cargo run --release --bin act_eval    -- traces/act*.json
```

外加 Python 那一层的离线自检（CI 也跑）：`.venv/Scripts/python.exe tools/advise_core.py --selftest`。

**第九条（`act_eval`，2026-09-12 加）判红，判据和第八条同一条：截断率必须 0**
（这里的分母是**链**不是仗）。它是 L3 阶段 3 的验收台，另外独占**回溯检验**
那一栏 —— 那一栏不判红，它报的是**偏的方向**（今天：预测每场比实测多掉 6.7 血）。
`--upgrade-check` 另跑整幕单调性自检，`--crn-off` 是它的归因臂
（把共享关掉，看死亡那一维塌回多少），两个都慢一倍、不进默认。

> **它照出过前八条全绿的错。** 2026-09-12 这台子第一次连着打几百场，
> 当场爆栈两次 —— 势不可当跟着敌人的格挡发作（`[源码]` 有 `creature == Owner`
> 而内核没有），加上触发器打出来的伤害把钩子层数重置成 0
> ⇒ 互相点火的环没有底。逐条见
> [verified-rules 的 2.11](verified-rules.md#211-触发器互相点火归属和层数2026-09-12)。
> **"没有一条验收会红"和"没有 bug"是两件事** —— 这一类环要绕很多圈才看得见，
> 而前八条最长的一条推演也只有 40 个回合。

**第八条（`fight_eval`，2026-09-10 加）判红，判据只有一条：截断率必须 0。**
它是 L3 阶段 2 的验收台 —— 把每一场仗**重新打 64 次**，报死亡率 / 血量分布 /
截断率。截断的推演战斗没打完而照样带着一个血量，那是本仓库最忌讳的
"自信地算错"。**别用 `--max-turns` 去消它**，理由见 [design-l3.md](design-l3.md) 的「L3：单场评估」。
`--upgrade-check` 另跑一遍单调性自检（基础牌全升，配对比），慢一倍，不进默认。

**第七条（`synth_audit`，2026-09-09 加）不判红**，它报的是「构造器缺什么」——
内容覆盖问题，和 `verify` 的 MISMATCH 不是一档。但它**独占一整类检验面**：
七条既有验收全部从 `Replayer::sync` 出发，于是「开局那一刻发生什么」
（第 1 回合的 `TurnStart`、遗物挂上来的 status、敌人的开局 status）
**在它们眼里结构上不存在** —— 语料的第一帧就已经在回合 1 里了。
它第一次跑就照出六条旧错，逐条见
[verified-rules 的 2.8](verified-rules.md#28-开局那一刻六条只有合成路径看得见的规则)。

> **两条运行环境的坑：**
>
> * **glob 要靠 shell 展开，验证器自己不认通配符。** 上面这些是 **bash** 命令。
>   PowerShell 不给原生 exe 展开 glob，直接跑会报 `os error 123`。
>   PowerShell 里要写成 `$f = (Get-ChildItem traces\act*.json).FullName;
>   .\target\release\verify.exe $f`。
> * **别写成 `traces/*.json`。** 那个目录里除了对拍语料还放着权威数据表
>   （`cards_catalog.json` 等），验证器会在它们身上报「不支持的 trace 版本 0」
>   然后停下。真修是把数据表挪进 `data/`，见 roadmap 的「小疙瘩」。

**为什么 rollout 要跑两遍**：P2 的方向判据只在 `--policy fast` 下上膛，见下表。

## 动了 planner 才跑的三条

编号接着上面九条往下数：第十条是 `--depth-sweep`（约 2 分半，上面那套加起来只要几十秒），第十一条是 `--alt` 同深度 A/B，第十二条是 `plan_audit`：

```bash
cargo run --release --bin rollout    -- traces/act*.json --policy plan --plan-depth 2 --depth-sweep 1
cargo run --release --bin rollout    -- traces/act*.json --policy plan --plan-depth 2 --alt "<改之前的那几个键>"
cargo run --release --bin rollout    -- traces/act*.json --policy plan --plan-depth 2 --set  "<改之前的那几个键>"   # 只量耗时
cargo run --release --bin plan_audit -- traces/act*.json
cargo run --release --bin plan_audit -- traces/act*.json --set "<改之前的那几个键>"   # 闸门：必须复现历史读数
```

**最后那一条是闸门，别跳过。** 把被测配置扳回改之前，`plan_audit` 的五个口径
必须**逐个数复现**上一版的读数 —— 对不上说明改动漏到了它不该碰的地方，
而那种错和"planner 有问题"长得一模一样。
阶段 3 用的是 `--set "cand-score=damage,k-certain=off,tt=off"`，
阶段 4 是 `--set "window-score=leaf"`。

第十一条是**同深度 A/B**：对照策略从主策略的配置出发，只改点名的键，
所以 P5 那一栏差出来的**只可能是这次改的东西**。改 planner 不跑它，
就只有"D=2 比 D=1 好多少"这一个数，而那个数对内部实现的改动近乎不动。

第十二条 `plan_audit`（约 10 分钟），它独占三件既有验收全都照不到的事 ——
**候选覆盖**尤其重要：不在候选集里的线，叶评估和目标函数评得再准也评不到，
所以那一栏对下游的一切改动免疫。`--inner` 再加一条"深层那一手是不是真口径下的
最优"，但很慢（第 2/3 幕语料约 25 分钟），只在动了深层选线时跑。

## 不进 CI 的上界参照：`bestline`

**问「这场仗最好能打成什么样」时才跑**（`bin/bestline`，
只对单场仗，几秒到几分钟）：

```bash
cargo run --release --bin bestline -- traces/<一场仗>.json --seeds 16 --beam 3000 --cands 40
cargo run --release --bin bestline -- traces/<一场仗>.json --seeds 64 --policies --pol-plan "k=16"
```

它**不是策略**：束搜索看得见这条随机轨迹的未来（添柴+ 生成什么它知道），
所以报的是「至少能打成这样」的**上界参照**。它独占的检验面是
**「策略离可达还差多少」** —— 前面十二条全是「策略自洽吗 / 比上一版好吗」，
一条都答不了这个。第 2 幕 Boss 那次就是它把「默认 D=2 在这场仗上 13/64」
和「束搜索 64/64」摆在一起，问题才从"planner 好像不太行"变成一个可修的数。

## 每一项独占的检验面

**这是这套验收的全部价值** —— 不然跑七遍也只是跑七遍。每一项都能证伪一类
别人证伪不了的东西：

| 项 | 独占什么 | 换句话说 |
|---|---|---|
| `cargo test` | 对拍照不到的单点规则 | 「头槌+ 能把自己捞回来」这种 bug **四种对拍模式全看不见**，只有单测守得住 |
| `verify` 一步预测 | 每一帧的**结果** | 观测太丰富，大部分错误当帧就抓得到 |
| `verify --per-turn` | **观测里没有、又会跨动作累积**的东西 | 牌区路由的累积错误、`CardInst.bonus`（暴走那种"这张牌本场变强"）。面很窄，别高估它 |
| `verify --predict-enemy` | 敌人**下一手是什么** | 不判"这一手打多少" |
| `bin/solve` | L2 的自洽性 | 「搜索穷尽时实战线不可能比求解线高分」—— 真出现了那不是"人打得比机器好"，是求解器有 bug |
| `bin/rollout` | **敌人在预测路径上打多少** | **前面全部沉默。** 实测过：把 `enemy_turn` 的攻击改成 −3，四种 trace 对拍模式一声不吭，只有这条红 |
| `bin/bestline` | **策略离「可达」还差多少** | 前九条量的都是「自洽 / 比上一版好」。**一个稳定地输掉某场仗的策略，在它们眼里可以全绿** —— 第 2 幕 Boss 就是这样：默认 D=2 在那场仗上 13/64，而束搜索 64/64 |
| `bin/fight_eval` | **那个局面打得完吗** | 前面每一条都在问"这一步/这一帧对不对"。它问的是**整场的结局分布** —— 而且是在**没有观测**的那条路上（构造器搭的局面）。它独占的硬判据是**截断率**：`bin/rollout` 的 P4 只覆盖语料里的回合起点，这里覆盖的是"凭牌组搭出来的开局" |
| `bin/act_eval` | **一整幕串起来** | 前面每一条最长只看一场仗（40 个回合封顶）。它连着打几百场，于是**只有绕很多圈才看得见的错**在这里才现形（触发器互相点火那两条 2026-09-12 就是它照出来的，前八条全绿）。它还独占**回溯检验**：实测战损落在预测分布的哪一档 —— 那是唯一一个把「我们这套策略」和**玩家**摆在一起量的数 |
| `bin/synth_audit` | **开局那一刻**：构造器凭牌组/遗物搭出来的局面对不对 | **前面全部从 `sync` 出发**，而 `sync` 每帧从观测重灌 status、第 1 回合的 `TurnStart` 只有 `begin_combat` 跑得到 ⇒ 这一整类规则从来没被检验过。它还独占三栏：遭遇表认不认得这场仗 · `asc::hp_range` 的区间对不对 · **开局第一手**（`--predict-enemy` 是拿观测到的第一个意图去*对齐*指针，开局那一手本身没验过） |

## 读这些数的五条

* **「结构上对」和「买到血」是两件事，别用前者去解释后者 —— 但这条不是死路，
  它是一张诊断单。** `deep_score` 那次把深层选线的错误关掉了 **75%**
  （4795 -> 1205），端到端 P5 同深度 A/B **均值 0.0**；确定性窗口那次自己那一栏
  22/45 -> 21/45、中位 915 -> 700，端到端 **−0.1**（325/349，噪声内且方向略负）。
  两次的诊断是同一句：到边界口径的最优根线有 **18–21/45 根本不在候选集里**，
  把一个被剪短了的候选集估得更准、搜得更深，都兑现不出来。
  **2026-09-05 阶段 3 照这张诊断单去修候选集，端到端当场从平局变成 +1.1 血**
  （3221 好 / 813 坏，≈4:1）—— 前两次不是白做的，它们是这一次的前提
  （筛子换成的那把尺子正是阶段 1 对齐好的那把）。
  **两个数都要记，只记好看的那个就是在骗下一个人**；而连着记三次，
  就能看出瓶颈在哪一层。
* **读数 3 判得了"搜索够不够好"，判不了"目标函数对不对"。**
  它量的是「A2（浅、按 `Plan::budget`）离 C（深、满预算）差多少」，
  **前提是两边同一个目标函数**。阶段 4 换的正是目标函数本身，于是它当场失效：
  两把尺子只在"赢下来的终局"上差一个常数 ⇒ 阶段 4 只可能改动**涉及赢的排序**
  ⇒ **不含 win 那一列结构上就看不见它**（实测两边逐字相同：n=8 均值 3346
  中位 1200 最大 14807），而含 win 那一列裁判和被测对象**按定义**不同意。
  这类改动的判据只有整场结局：**P5（最终血量）+ P4（截断率）**。
  路线图当初给阶段 4 定的判据就是定错在这里，教训记在 verification-log。
* **`plan_audit` 读数 3 有个下限，别拿它和 0 比。** 到边界最优根线不在候选集时
  后悔必然 > 0，所以「后悔>0」最低只能降到 `miss_c`（阶段 3 之后 6/45，
  之前是 20/45）。报告里会把这个下限和"离下限还有几个起点"一起印出来。
  **那个差才是目标函数和深度还能动的部分** —— 阶段 2 结束时是 1 个，
  阶段 3 之后是 4 个。候选生成先做完，下游两阶段才有东西可买。
* **同一次改动里，「个数」和「幅度」可以往相反方向走。** 阶段 3a 把后悔>0 的
  个数从 21 降到 20，而不含 win 的中位从 700 涨到 **1200** —— 留下的那批起点
  换了一组，剩下的更难啃。**只报个数就是在挑好看的那个。**
* **「一致 46」不是独立证据。** 那一栏会涨只是因为我照着 `--live` 打 ——
  两条线当然更容易重合。**判据始终是「0 例实战线赢过穷尽搜索」那一行。**
* **「换序 0」不是求解器退步了，是语料的构成变了。** 那一栏只在我自己也选对了牌、
  只是顺序打错时才会亮；第 2/3 幕求解器几乎总能找到一堆**不同的**牌（另选 134），
  换序没有机会出现。
* **敌人 AI 那几行必须一起读。** 集合越大越容易命中，把集合开到全表也能拿 100%。
  **1.10 就是那个百分比的含金量。** 真正该看的是**落在集合外 / 未知 / 对不齐**
  这三个数 —— 其中**落在集合外今天是 6 例、对不齐是 1 只**，都不是 0，
  别把它读成满分。
  （这个百分比**口径换过两次，不能和历史值直接比**，见 verification-log。）
* **P3「策略线 ≥ 实战线」跌了不一定是回归。** 它用**单回合目标函数**给线打分，
  而能力牌按定义在那个口径下就是亏的 —— 策略开始打能力牌，这一栏必然跌。
  **判据是 P3(a)(b) 那两个 0。**

## 全绿不等于内核对了

它只说明**语料照得到的地方**没有分歧。已知还欠、而且**偏向都是乐观**的：

* 永世沙漏「剧烈增强」的力量递增（真实 3/4/5…，内核恒 +3，欠一个非观测量的计数器）。
  **2026-09-06 实测钉住了**：同一场里 Boss 力量 0 -> 3 -> **7**，第二次给的是 +4。

## 两条别踩的

* **录完 trace 当场跑全套，别信文档里的绿灯。** 2026-08-29 那次两帧红躺了一天多，
  就是因为录完没跑、而文档写于那之前。
* **"这一帧绿了"不等于"这条规则对了"。** 修坚定不移时青蛙骑士那一帧转绿，有一半
  是同步清零**凑巧给对了答案**。同理，**内容覆盖率 ≠ 行为覆盖率** ——
  补内容会把旧错误照出来（敌人不在表里时整帧算「内容缺失」，一补就红）。

## 被动语料不进默认 glob

`traces/passive_*.json`（玩家自己驾驶、动作是**反推**的）**证据档次比驱动语料低
一档**，`act*.json` 不匹配它。要判得显式写文件名，**读它的红先怀疑动作**。
